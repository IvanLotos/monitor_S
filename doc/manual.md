# Аналитическая пояснительная записка

**Версия:** 2.2.0 
**Дата:** 2026-08-26 
**Соответствует версии сервера:** 2.1.0

---

## 1. Введение

Назначение сервера S – предоставление единого HTTP API для получения результатов проверок работоспособности и доступности сервисов в распределённой инфраструктуре. Сервер агрегирует данные от множества независимых модулей-проверок (TCP-порты, DNS-разрешение, HTTP-статусы и др.), кэширует результаты и отдаёт их по запросу, минимизируя задержки и нагрузку на целевые системы.

Основные задачи:
- Сбор и агрегация данных от различных источников (модулей) в единый формат.
- Кэширование результатов в оперативной памяти для обеспечения мгновенных ответов.
- Разделение операций обновления данных (фоновое и по требованию) и операций чтения (все GET-запросы).
- Гибкая фильтрация данных по операциям и группам хостов для снижения объёма передаваемой информации.
- Модульная архитектура, позволяющая легко добавлять новые проверки без изменения ядра.
- **Горячая перезагрузка конфигурации без остановки сервера (с версии 2.1.0).**
- **Поддержка модулей, использующих внешние источники данных через защищённые каналы (mTLS) – например, модуль `local_listener_check` (с версии 2.2.0).**

Место в экосистеме мониторинга: 
S выступает в роли агрегатора и кэширующего прокси между системами мониторинга (например, Grafana через Infinity datasource) и целевыми сервисами. Он берёт на себя периодический сбор данных, снижая нагрузку на сеть и проверяемые системы, а также обеспечивает единый формат ответов для различных источников.

## 2. Ключевые принципы работы

- **Модульность.** Каждый модуль – независимый компонент, реализующий конкретную проверку. Модули загружаются динамически из папки modules/ при старте сервера. Они не зависят друг от друга и не влияют на ядро.
- **Кэширование.** Все результаты проверок хранятся в оперативной памяти в структурированном виде. Фоновая задача обновляет кэш с заданной периодичностью. Также предусмотрен эндпоинт /refresh для принудительного обновления.
- **Разделение операций чтения и обновления.** Все GET-запросы (кроме /refresh) являются лёгкими – они только читают кэш и возвращают данные мгновенно (время ответа – миллисекунды). Эндпоинт /refresh (доступен как GET, так и POST) инициирует синхронное выполнение всех модулей и обновление кэша. Это гарантирует предсказуемую скорость ответа для систем мониторинга.
- **Фильтрация по группам.** Позволяет запрашивать результаты только для хостов, в имени которых (в первом лейбле FQDN) содержится заданный суффикс или подстрока. Например, запрос /v3/portcheck/PGL вернёт данные только для хостов, содержащих PGL в первом лейбле (регистронезависимо). Это снижает объём передаваемых данных и ускоряет ответ.
- **Горячая перезагрузка конфигурации.** (С версии 2.1.0) Сервер может перезагружать основной конфиг и конфиги модулей без остановки, при этом запрещено изменение критических параметров (host, port, max_workers, refresh_interval, modules_dir, config_watch_interval).
- **Поддержка защищённых каналов с mTLS.** (С версии 2.2.0) Модуль `local_listener_check` использует взаимную аутентификацию по сертификатам для опроса удалённых агентов мониторинга, что обеспечивает безопасность и соответствие корпоративным стандартам.

## 3. Логическая модель данных

Формат ключей в модулях:
- Общий вид: {префикс_операции}.{хост}.{порт} (если порт применим). Пример: portcheck.ims-g201AQL.22, dns.ims-g201AQL.
- Для HTTP-модуля, где на одном хосте:порту может быть несколько эндпоинтов, ключ дополняется методом и путём: {prefix}.{first_label}.{port}.{method}.{path_escaped}. Пример: http.jolokia-host.8161.POST._console_jolokia.
- Для модуля `local_listener_check` ключи имеют вид `listener.{first_label}.{port}` (префикс настраивается). Это позволяет использовать стандартную фильтрацию по группам.

Структура кэша в памяти: 
Кэш представляет собой вложенный словарь, где верхний уровень – операции (модули), второй уровень – хосты, третий (если есть) – порты или детали:

```json
{
  "timestamp": "2026-08-17T12:00:00",
  "portcheck": {
    "ims-g201AQL": {"22": true, "6060": false}
  },
  "http": {
    "jolokia-host": {"8161.POST._console_jolokia": true}
  },
  "listener": {
    "web1": {"22": true, "8080": false}
  }
}

Форматы ответов API:

Эндпоинт |	Формат|	Описание
---| ----| ----
/	| Массив { "ключ": значение }|	Устаревший формат для обратной совместимости
/v2	| Массив { "operation": "...", "host": "...", "value": { ... } }|	Группировка портов в объект для каждого хоста
/v3	| Массив { "operation": "...", "host": "...", "value": "...", "port": "..." }|	Каждая пара (хост, порт) – отдельная запись
/v3/{op}|	|То же, что /v3, но только для указанной операции	Фильтрация по операции
/v3/{op}/{groups}| |	То же, с дополнительной фильтрацией по группам хостов	Фильтрация по подстроке в первом лейбле

## 4. Архитектура системы

Компоненты:

    Ядро S – HTTP-сервер на базе Python, отвечающий за приём запросов, управление кэшем, загрузку модулей, фоновую задачу и многопоточную обработку.

    Модули – отдельные Python-файлы, каждый содержит функцию run(config) -> dict, выполняющую проверку и возвращающую словарь с результатами.

    Кэш – глобальный словарь в памяти, защищённый блокировкой RLock, обеспечивающий быстрый и безопасный доступ.

    Фоновая задача обновления кэша – поток, периодически запускающий обновление кэша (выполнение всех модулей) с заданным интервалом (refresh_interval).

    Config Watcher – фоновый поток, отслеживающий изменения в YAML-конфигурационных файлах. Поддерживает горячую перезагрузку конфигурации без остановки сервера (добавлен в версии 2.1.0).

    Многопоточный HTTP-сервер – на базе socketserver.ThreadingMixIn с ограничением числа одновременных запросов (max_workers).

Особенности модуля local_listener_check:

    Относится к категории модулей, опрашивающих внешние источники по HTTPS с mTLS.

    Не выполняет прямое сканирование портов, а использует данные, собранные агентами мониторинга.

    Поддерживает переопределение порта агента и путей к сертификатам на уровне хоста, что обеспечивает гибкость в гетерогенных средах.

Взаимодействие компонентов:

· При старте S загружает модули из папки modules/, считывает их конфиги и сохраняет в глобальную структуру.
· Запускается фоновый поток обновления кэша, который сразу выполняет первое обновление, затем повторяет его с интервалом refresh_interval.
· Запускается поток Config Watcher, который периодически (с интервалом config_watch_interval) проверяет изменения в файлах config.yaml и всех модульных .yaml. При обнаружении изменений выполняется горячая перезагрузка конфигурации (без остановки сервера).
· HTTP-запросы обрабатываются параллельно (до max_workers одновременно). Все GET-запросы читают кэш (блокировка на чтение), а /refresh выполняет модули синхронно и обновляет кэш (блокировка на запись).
· Модули выполняются с таймаутом (module_timeout), чтобы избежать зависаний.
## 5. Сценарии использования

· Мониторинг доступности сервисов: проверка TCP-портов (SSH, HTTP, базы данных), DNS-разрешений, HTTP-статусов (с проверкой содержимого) на множестве хостов.
· Интеграция с Grafana через Infinity datasource: быстрые GET-запросы к /v3/{op}/{groups} для отображения статусов в панелях. Настройка автоматического обновления через фоновое кэширование.
· Принудительное обновление данных: использование эндпоинта /refresh по расписанию (например, через cron) или вручную для синхронизации кэша.
· Тестирование и отладка: использование модуля dummy для генерации тестовых данных или модуля gettime для получения временных меток.
· Горячее обновление конфигурации: администратор может изменять параметры (кроме запрещённых) без остановки сервера, что минимизирует простои.
· Проверка наличия локальных портов через агентов мониторинга – с помощью модуля local_listener_check можно централизованно контролировать, какие порты на loopback-интерфейсе слушают на удалённых хостах, используя уже развёрнутых агентов.

## 6. Ограничения и допущения

· Размер кэша не ограничен явно – хранится в оперативной памяти; для больших инфраструктур рекомендуется мониторинг использования памяти.
· Максимальное число групп в одном запросе – 10 суффиксов (для защиты от перегрузки).
· Таймаут модулей: каждый модуль должен завершиться за module_timeout (по умолчанию 30 сек). Превышение приводит к игнорированию результатов и логированию ошибки.
· Однопоточное выполнение модулей внутри ядра: каждый модуль вызывается последовательно, но автор модуля может использовать внутреннюю многопоточность.
· Зависимость от сети и сторонних систем: модули могут зависеть от доступности проверяемых хостов и сервисов, что может влиять на время обновления кэша.
· Регистр групп при фильтрации не учитывается (все строки приводятся к верхнему регистру).
· Горячая перезагрузка не применяется для параметров host, port, server.max_workers, cache.refresh_interval, modules_dir, config_watch_interval – их изменение требует ручного рестарта. При попытке изменения этих параметров через горячую перезагрузку изменения игнорируются, а в лог выводится ошибка.
· При ошибке синтаксиса в YAML изменения не применяются, сервер продолжает работать со старой конфигурацией.
· Для модуля local_listener_check необходимо, чтобы на каждом хосте был доступен агент мониторинга, работающий по HTTPS с mTLS. Если агент недоступен, все проверяемые порты на данном хосте считаются отсутствующими.

## 7. Безопасность и производительность

· CORS – включены заголовки Access-Control-Allow-Origin: *, что позволяет использовать API из браузерных приложений и Grafana.
· Ограничение числа одновременных запросов – параметр server.max_workers (по умолчанию 20) предотвращает перегрузку сервера.
· Таймауты на выполнение модулей и фоновых задач защищают систему от зависаний.
· Config Watcher использует polling с интервалом не менее 60 секунд (рекомендуется), что не создаёт значительной нагрузки на CPU.
· Многопоточность обеспечивает параллельную обработку запросов, но ограничена семафором для контроля нагрузки.
· Учётные данные (пароли) хранятся в отдельном файле с правами 600, используются через ссылки auth_ref, маскируются в логах.
· Модуль local_listener_check использует mTLS для безопасного соединения с агентами, что гарантирует конфиденциальность и целостность данных, а также взаимную аутентификацию. При необходимости пути к сертификатам могут быть переопределены для каждого хоста.

## 8. Заключение

Сервер S представляет собой гибкое, производительное и масштабируемое решение для агрегации данных мониторинга. Его архитектура, основанная на модульности и кэшировании, позволяет легко адаптироваться к изменениям инфраструктуры и минимизировать нагрузку на системы. Рекомендуется к использованию в средах с большим количеством хостов и высокими требованиями к скорости отклика.

Дорожная карта развития:

· Добавление аутентификации (API-ключи) для защиты эндпоинтов.
· Возможность хранения кэша во внешнем хранилище (Redis) для масштабирования.
· Расширение форматов фильтрации (регулярные выражения, исключения).
· Добавление метрик Prometheus для мониторинга состояния самого S.
· Эндпоинт для получения текущей конфигурации (/config) – планируется.
