# Руководство программиста сервера S

**Версия документации:** 2.2.0 
**Дата:** 2026-08-26 
**Соответствует версии сервера:** 2.1.0

---

## 1. Введение

Руководство предназначено для разработчиков, создающих новые модули для сервера S, а также для тех, кто хочет понять внутреннее устройство системы или модифицировать её.

S – это модульный HTTP-сервер с кэшированием. Ядро обеспечивает загрузку модулей, управление кэшем, многопоточную обработку запросов и фоновое обновление. Модули – это независимые компоненты, каждый из которых реализует функцию `run(config) -> dict`, возвращающую результаты проверок.

**Важно:** С версии 2.1.0 сервер поддерживает горячую перезагрузку конфигурации (без остановки). Это означает, что конфиги модулей могут перезагружаться на лету, но код модулей при этом не перезагружается.

**С версии 2.2.0** в состав включён модуль `local_listener_check`, демонстрирующий использование внешних HTTPS-запросов с mTLS и работу с данными агентов. Его архитектура может служить примером для создания подобных модулей.

## 2. Логическая модель и архитектура

Поток данных:
- GET-запрос → обработчик → чтение глобального кэша (CACHE) → формирование ответа → отправка.
- /refresh → синхронный вызов update_cache() → выполнение всех модулей → запись в CACHE → ответ.

Глобальные структуры:
- `MODULES` – словарь, где ключ – имя модуля (нормализованное, без подчёркиваний), значение – словарь с полями `run` (функция), `config` (конфиг модуля), `version`, `config_path`.
- `CACHE` – словарь, структурированный как `{operation: {host: value_or_dict}}`, защищённый блокировкой `CACHE_LOCK` (RLock).
- `CACHE_TIMESTAMP` – строка ISO с временем последнего обновления.
- `GLOBAL_CONFIG` – глобальный конфиг сервера. При горячей перезагрузке (если включена) он может быть обновлён без рестарта.

Блокировки: `CACHE_LOCK` используется при чтении (копирование кэша) и записи (обновление). Для чтения достаточно блокировки на время копирования. `CONFIG_LOCK` (добавлен в версии 2.1.0) защищает обновление глобальной конфигурации.

## 3. Интерфейс модуля

Каждый модуль должен предоставлять функцию:

```python
def run(config: dict) -> dict:
   ...
```
· config – словарь, загруженный из файла конфигурации модуля (YAML или JSON).
· Возвращаемое значение – словарь, где ключи – строки, значения – любые JSON-сериализуемые (bool, int, float, str, dict, list).

Правила формирования ключей:
Для совместимости с фильтрацией по группам и форматами ответов рекомендуется использовать префикс операции и имя хоста (и порт, если применимо):

· {префикс}.{хост} – для операций без порта.
· {префикс}.{хост}.{порт} – для операций с портами.
· Для модуля http_check с несколькими эндпоинтами на одном хосте:порту ключ дополняется методом и путём: {prefix}.{first_label}.{port}.{method}.{path_escaped}.

Примеры:

· Модуль DNS: {"dns.ims-g201AQL": True, "dns.ims-g202KFL": False}
· Модуль portcheck: {"portcheck.ims-g201AQL.22": True, "portcheck.ims-g201AQL.6060": False}
· Модуль http: {"http.jolokia-host.8161.POST._console_jolokia": True}
· Модуль local_listener_check: {"listener.web1.22": True, "listener.web1.8080": False}

Префикс должен быть уникальным среди модулей.

## 4. Конфигурация модуля

Файл конфигурации должен иметь то же имя, что и модуль, с расширением .yaml (или .json). Например, для portcheck.py – portcheck.yaml.

Рекомендуется включать параметры:

· prefix – строковый префикс для ключей.
· hosts или endpoints – список целевых объектов (хосты, порты, пути).
· Специфичные для модуля параметры (таймауты, пути, и т.д.).

Важно: При горячей перезагрузке конфигурации (если включена) файл .yaml модуля перечитывается, но сам .py файл не перезагружается. Это означает, что изменения в логике модуля требуют ручного перезапуска сервера, а изменения в конфигурации применяются автоматически.

Пример конфигурации модуля local_listener_check:
```yaml

prefix: "listener"
cert_path: "/etc/ssl/default/client.crt"
key_path: "/etc/ssl/default/client.key"
ca_chain_path: "/etc/ssl/default/ca-chain.pem"
agent_port: 9500
timeout: 5
max_workers: 20
ports:
  - 22
  - 8080
hosts:
  - host: "web1.my.company.com"
  - host: "web2.my.company.com"
    agent_port: 9501
    ports:
      - 443
```

## 5. Версионирование

Каждый модуль должен содержать глобальную переменную VERSION (строку). Она отображается в логах при загрузке.

Рекомендуется использовать семантическое версионирование (MAJOR.MINOR.PATCH):

· MAJOR – несовместимые изменения (например, изменение формата возвращаемых данных).
· MINOR – добавление новой функциональности без нарушения совместимости.
· PATCH – исправления ошибок.

## 6. Разработка нового модуля: пошаговая инструкция

    Создайте файл в папке modules/, например, my_check.py.

    Реализуйте функцию run(config).

    Добавьте переменную VERSION.

    Организуйте логирование с использованием logger = logging.getLogger(name).

    Создайте конфиг my_check.yaml в той же папке.

    Протестируйте модуль изолированно (вызовите run с тестовым конфигом).

    Запустите сервер и проверьте, что модуль загружается и его данные появляются в ответах.

    Используйте таймауты и обработку исключений для сетевых операций.

    Учитывайте, что ваш модуль может быть перезагружен (только конфиг) без перезапуска сервера. Убедитесь, что модуль корректно обрабатывает обновление конфигурации на лету. Например, если модуль кеширует какие-то данные из конфига, их нужно перечитывать при каждом вызове run.

Шаблон модуля:
```python

import logging

VERSION = "1.0.0"
logger = logging.getLogger(__name__)

def run(config: dict) -> dict:
    logger.info("Module started")
    # Ваша логика
    result = {}
    # ... заполнение result
    logger.info("Module finished, returning %d keys", len(result))
    return result
```

Пример модуля, использующего mTLS и внешние HTTPS-запросы, – local_listener_check. Его полное описание приведено в Приложении 2. 
Он демонстрирует:

    Создание кастомного HTTPAdapter для настройки SSL-контекста.

    Параллельный опрос хостов с помощью ThreadPoolExecutor.

    Переопределение параметров (порт, сертификаты) на уровне хоста.

    Обработку ошибок и логирование.

## 7. Расширенные возможности

· Параллелизм внутри модуля. Для ускорения проверок используйте concurrent.futures.ThreadPoolExecutor (как в модуле portcheck или http_check). Это безопасно, т.к. модули выполняются в отдельных потоках ядра.
· Таймауты. Устанавливайте собственные таймауты на сетевые операции (например, параметр timeout в socket.create_connection или requests), чтобы не полагаться только на общий module_timeout.
· Логирование. Используйте разные уровни (debug, info, warning, error) для отладки и мониторинга.
· Секреты. Для хранения учётных данных предусмотрите механизм, аналогичный http_check: отдельный файл с правами 600 и ссылки через auth_ref. В модуле вы можете использовать функцию load_secrets для чтения секретов.
· mTLS. Для защищённых соединений используйте кастомный HTTPAdapter с настройкой SSL-контекста, как в модуле local_listener_check.

## 8. Тестирование и отладка модуля

· Локальный запуск: импортируйте модуль и вызовите run с тестовым конфигом в отдельном скрипте.
· Включение DEBUG логов: установите в config.yaml для вашего модуля уровень DEBUG, чтобы видеть все сообщения.
· Проверка совместимости: убедитесь, что возвращаемые ключи соответствуют ожидаемым форматам для /v2 и /v3 (особенно для портов).
· Для модулей с mTLS используйте curl с теми же сертификатами для проверки доступности конечной точки.

## 9. Структура файлов и каталогов
```text

/opt/s/
├── server.py
├── config.yaml
├── modules/
│   ├── dns_check.py
│   ├── dns.yaml
│   ├── port_check.py
│   ├── portcheck.yaml
│   ├── http_check.py
│   ├── http_check.yaml
│   ├── local_listener_check.py
│   ├── local_listener_check.yaml
│   ├── dummy.py
│   ├── dummy.yaml
│   ├── gettime.py
│   └── gettime.yaml
└── logs/
    └── server.log
```
· Имена модулей нормализуются ядром (убираются подчёркивания). Например, dns_check → dns, http_check → http, local_listener_check → locallistenercheck. Это важно для эндпоинтов /v3/{operation}.
· Конфиги модулей должны иметь то же имя, что и файл модуля, но с расширением .yaml (или .json).
