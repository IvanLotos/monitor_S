## 1. Введение

Назначение сервера S – предоставление единого HTTP API для получения результатов проверок работоспособности и доступности сервисов в распределённой инфраструктуре. Основные задачи:
- Сбор и агрегация данных от различных источников (модулей) в единый формат.

## 2. Ключевые принципы работы

- **Модульность.** Каждый модуль – независимый компонент, реализующий конкретную проверку. Модули загружаются динамически из папки modules/ при старте сервера. Они не зависят друг от друга и не влияют на ядро.
- **Кэширование.** Все результаты проверок хранятся в оперативной памяти в структурированном виде. Фоновая задача обновляет кэш с заданной периодичностью. Также предусмотрен эндпоинт /refresh для принудительного обновления.
- **Разделение операций чтения и обновления.** Все GET-запросы (кроме /refresh) являются лёгкими – они только читают кэш и возвращают данные мгновенно (время ответа – миллисекунды). Эндпоинт /refresh (доступен как GET, так и POST) инициирует синхронное выполнение всех модулей и обновление кэша. Это гарантирует предсказуемую скорость ответа для систем мониторинга.
- **Фильтрация по группам.** Позволяет запрашивать результаты только для хостов, в имени которых (в первом лейбле FQDN) содержится заданный суффикс или подстрока. Например, запрос /v3/portcheck/PGL вернёт данные только для хостов, содержащих PGL в первом лейбле (регистронезависимо). Это снижает объём передаваемых данных и ускоряет ответ.
- **Горячая перезагрузка конфигурации.** (С версии 2.1.0) Сервер может перезагружать основной конфиг и конфиги модулей без остановки, при этом запрещено изменение критических параметров (host, port, max_workers, refresh_interval, modules_dir, config_watch_interval).

4. Архитектура системы

Компоненты:

1. Ядро S – HTTP-сервер на базе Python, отвечающий за приём запросов, управление кэшем, загрузку модулей, фоновую задачу и многопоточную обработку.
2. Модули – отдельные Python-файлы, каждый содержит функцию run(config) -> dict, выполняющую проверку и возвращающую словарь с результатами.
3. Кэш – глобальный словарь в памяти, защищённый блокировкой RLock, обеспечивающий быстрый и безопасный доступ.
4. Фоновая задача обновления кэша – поток, периодически запускающий обновление кэша (выполнение всех модулей) с заданным интервалом (refresh_interval).
5. Config Watcher – фоновый поток, отслеживающий изменения в YAML-конфигурационных файлах. Поддерживает горячую перезагрузку конфигурации без остановки сервера (добавлен в версии 2.1.0).
6. Многопоточный HTTP-сервер – на базе socketserver.ThreadingMixIn с ограничением числа одновременных запросов (max_workers).

Взаимодействие компонентов:

· При старте S загружает модули из папки modules/, считывает их конфиги и сохраняет в глобальную структуру.
· Запускается фоновый поток обновления кэша, который сразу выполняет первое обновление, затем повторяет его с интервалом refresh_interval.
· Запускается поток Config Watcher, который периодически (с интервалом config_watch_interval) проверяет изменения в файлах config.yaml и всех модульных .yaml. При обнаружении изменений выполняется горячая перезагрузка конфигурации (без остановки сервера).
· HTTP-запросы обрабатываются параллельно (до max_workers одновременно). Все GET-запросы читают кэш (блокировка на чтение), а /refresh выполняет модули синхронно и обновляет кэш (блокировка на запись).
· Модули выполняются с таймаутом (module_timeout), чтобы избежать зависаний.

6. Ограничения и допущения

· Размер кэша не ограничен явно – хранится в оперативной памяти; для больших инфраструктур рекомендуется мониторинг использования памяти.

· Таймаут модулей: каждый модуль должен завершиться за module_timeout (по умолчанию 30 сек). Превышение приводит к игнорированию результатов и логированию ошибки.
· Однопоточное выполнение модулей внутри ядра: каждый модуль вызывается последовательно, но автор модуля может использовать внутреннюю многопоточность.
· Зависимость от сети и сторонних систем: модули могут зависеть от доступности проверяемых хостов и сервисов, что может влиять на время обновления кэша.
· Регистр групп при фильтрации не учитывается (все строки приводятся к верхнему регистру).
· Горячая перезагрузка не применяется для параметров host, port, server.max_workers, cache.refresh_interval, modules_dir, config_watch_interval – их изменение требует ручного рестарта. При попытке изменения этих параметров через горячую перезагрузку изменения игнорируются, а в лог выводится ошибка.
· При ошибке синтаксиса в YAML изменения не применяются, сервер продолжает работать со старой конфигурацией.

· CORS – включены заголовки Access-Control-Allow-Origin: *, что позволяет использовать API из браузерных приложений и Grafana.
· Ограничение числа одновременных запросов – параметр server.max_workers (по умолчанию 20) предотвращает перегрузку сервера.
· Таймауты на выполнение модулей и фоновых задач защищают систему от зависаний.
· Config Watcher использует polling с интервалом не менее 60 секунд (рекомендуется), что не создаёт значительной нагрузки на CPU.
· Многопоточность обеспечивает параллельную обработку запросов, но ограничена семафором для контроля нагрузки.
· Учётные данные (пароли) хранятся в отдельном файле с правами 600, используются через ссылки auth_ref, маскируются в логах.

3. Конфигурация

Файл config.yaml содержит все настройки сервера. Пример с пояснениями:

```yaml

port: 8080                      # Порт

4. Автоматическое отслеживание изменений конфигурации (горячая перезагрузка)

Сервер поддерживает горячую перезагрузку конфигурационных файлов (основного config.yaml и всех модульных .yaml) без остановки сервера.

Параметр config_watch_interval

Определяет режим работы:

· -1 – отслеживание отключено. Изменения конфигов требуют ручного перезапуска сервера.
· 0 – включён режим только логирования. Сервер проверяет файлы каждые 60 секунд и при обнаружении изменений записывает в лог сообщение с путём и временем изменения, но не перезагружает конфигурацию.
· >=60 – включён режим автоматической перезагрузки. Сервер проверяет файлы с заданным интервалом (в секундах). При обнаружении изменений выполняется перезагрузка GLOBAL_CONFIG и конфигов модулей (без перезагрузки кода модулей). Если интервал меньше 60, выводится предупреждение, но значение используется как есть.

Что перезагружается?

· Обновляется содержимое GLOBAL_CONFIG (все параметры, кроме запрещённых).
· Обновляются конфиги каждого модуля (загружаются из соответствующих .yaml файлов).
· Кэш (CACHE) не трогается – он обновится по расписанию.
· Код модулей не перезагружается (только их конфиги).

Запрещённые для горячей перезагрузки параметры

Следующие параметры не могут быть изменены через горячую перезагрузку и требуют ручного рестарта:

· host
· port
· server.max_workers
· cache.refresh_interval
· modules_dir
· config_watch_interval

При попытке их изменения в конфиге сервер залогирует ошибку и оставит старые значения.

Обработка ошибок

· При синтаксической ошибке в YAML изменения не применяются, сервер продолжает работать со старой конфигурацией, ошибка логируется.
· Если модульный конфиг повреждён или отсутствует, перезагрузка отменяется, и сервер остаётся на старых конфигах (с логированием ошибки).

Логирование событий

Типовые сообщения, связанные с работой вотчера:

· Config watcher started with interval 60s – запущен наблюдатель.
· Config file changed: config.yaml (mtime: ... -> ...) – обнаружено изменение файла.
· Configuration reloaded successfully – перезагрузка выполнена успешно.
· Forbidden configuration change detected: ... – попытка изменить запрещённый параметр.
· YAML parsing error in config file: ... – ошибка синтаксиса.

### Документ 3. Руководство программиста (полная версия с изменениями)

```markdown
# Руководство программиста сервера S

**Версия документации:** 2.1.0 
**Дата:** 2026-08-23 
**Соответствует версии сервера:** 2.1.0

---

## 1. Введение

Руководство предназначено для разработчиков, создающих новые модули для сервера S, а также для тех, кто хочет понять внутреннее устройство системы или модифицировать её.

S – это модульный HTTP-сервер с кэшированием. Ядро обеспечивает загрузку модулей, управление кэшем, многопоточную обработку запросов и фоновое обновление. Модули – это независимые компоненты, каждый из которых реализует функцию `run(config) -> dict`, возвращающую результаты проверок.

**Важно:** С версии 2.1.0 сервер поддерживает горячую перезагрузку конфигурации (без остановки). Это означает, что конфиги модулей могут перезагружаться на лету, но код модулей при этом не перезагружается.

---

## 2. Логическая модель и архитектура

Поток данных:
- GET-запрос → обработчик → чтение глобального кэша (CACHE) → формирование ответа → отправка.
- /refresh → синхронный вызов update_cache() → выполнение всех модулей → запись в CACHE → ответ.

Глобальные структуры:
- `MODULES` – словарь, где ключ – имя модуля (нормализованное, без подчёркиваний), значение – словарь с полями `run` (функция), `config` (конфиг модуля), `version`, `config_path`.
- `CACHE` – словарь, структурированный как `{operation: {host: value_or_dict}}`, защищённый блокировкой `CACHE_LOCK` (RLock).
- `CACHE_TIMESTAMP` – строка ISO с временем последнего обновления.
- `GLOBAL_CONFIG` – глобальный конфиг сервера. При горячей перезагрузке (если включена) он может быть обновлён без рестарта.

Блокировки: `CACHE_LOCK` используется при чтении (копирование кэша) и записи (обновление). Для чтения достаточно блокировки на время копирования. `CONFIG_LOCK` (добавлен в версии 2.1.0) защищает обновление глобальной конфигурации.

---

## 3. Интерфейс модуля

Каждый модуль должен предоставлять функцию:

```python
def run(config: dict) -> dict:
    ...
```

· config – словарь, загруженный из файла конфигурации модуля (YAML или JSON).
· Возвращаемое значение – словарь, где ключи – строки, значения – любые JSON-сериализуемые (bool, int, float, str, dict, list).

Правила формирования ключей:
Для совместимости с фильтрацией по группам и форматами ответов рекомендуется использовать префикс операции и имя хоста (и порт, если применимо):

· {префикс}.{хост} – для операций без порта.
· {префикс}.{хост}.{порт} – для операций с портами.
· Для модуля http_check с несколькими эндпоинтами на одном хосте:порту ключ дополняется методом и путём: {prefix}.{first_label}.{port}.{method}.{path_escaped}.

Примеры:

· Модуль DNS: {"dns.ims-g201AQL": True, "dns.ims-g202KFL": False}
· Модуль portcheck: {"portcheck.ims-g201AQL.22": True, "portcheck.ims-g201AQL.6060": False}
· Модуль http: {"http.jolokia-host.8161.POST._console_jolokia": True}

Префикс должен быть уникальным среди модулей.

---

4. Конфигурация модуля

Файл конфигурации должен иметь то же имя, что и модуль, с расширением .yaml (или .json). Например, для portcheck.py – portcheck.yaml.

Рекомендуется включать параметры:

· prefix – строковый префикс для ключей.
· hosts или endpoints – список целевых объектов (хосты, порты, пути).
· Специфичные для модуля параметры (таймауты, пути, и т.д.).

Важно: При горячей перезагрузке конфигурации (если включена) файл .yaml модуля перечитывается, но сам .py файл не перезагружается. Это означает, что изменения в логике модуля требуют ручного перезапуска сервера, а изменения в конфигурации применяются автоматически.

Пример http_check.yaml:

```yaml
prefix: "http"
secrets_file: "/etc/s/secrets.yaml"
max_workers: 20
log_level: "summary"
defaults:
  timeout: 3
  method: "GET"
  expected_status: 200
  ssl: auto
  check_content: null
  headers: {}
endpoints:
  - host: "jolokia-host.example.com"
    port: 8161
    path: "/console/jolokia"
    method: "POST"
    ssl: true
    auth_ref: "jolokia_creds"
    headers:
      Origin: "https://jolokia-host.example.com:8161"
    body: '{"type":"read","mbean":"java.lang:type=Memory"}'
```

5. Версионирование

Каждый модуль должен содержать глобальную переменную VERSION (строку). Она отображается в логах при загрузке.

Рекомендуется использовать семантическое версионирование (MAJOR.MINOR.PATCH):

· MAJOR – несовместимые изменения (например, изменение формата возвращаемых данных).
· MINOR – добавление новой функциональности без нарушения совместимости.
· PATCH – исправления ошибок.

---

6. Разработка нового модуля: пошаговая инструкция

1. Создайте файл в папке modules/, например, my_check.py.
2. Реализуйте функцию run(config).
3. Добавьте переменную VERSION.
4. Организуйте логирование с использованием logger = logging.getLogger(__name__).
5. Создайте конфиг my_check.yaml в той же папке.
6. Протестируйте модуль изолированно (вызовите run с тестовым конфигом).

7. Расширенные возможности

· Параллелизм внутри модуля. Для ускорения проверок используйте concurrent.futures.ThreadPoolExecutor (как в модуле portcheck или http_check). Это безопасно, т.к. модули выполняются в отдельных потоках ядра.
· Таймауты. Устанавливайте собственные таймауты на сетевые операции (например, параметр timeout в socket.create_connection или requests), чтобы не полагаться только на общий module_timeout.
· Логирование. Используйте разные уровни (debug, info, warning, error) для отладки и мониторинга.
· Секреты. Для хранения учётных данных предусмотрите механизм, аналогичный http_check: отдельный файл с правами 600 и ссылки через auth_ref. В модуле вы можете использовать функцию load_secrets для чтения секретов.
