1. Аналитическая пояснительная записка

1. Введение

    Назначение сервера S – предоставление единого HTTP API для получения результатов проверок работоспособности и доступности сервисов в распределённой инфраструктуре. Сервер агрегирует данные от множества независимых модулей-проверок (TCP-порты, DNS-разрешение, HTTP-статусы и др.), кэширует результаты и отдаёт их по запросу, минимизируя задержки и нагрузку на целевые системы.

    Основные задачи:

    · Сбор и агрегация данных от различных источников (модулей) в единый формат.
    · Кэширование результатов в оперативной памяти для обеспечения мгновенных ответов.
    · Разделение операций обновления данных (фоновое и по требованию) и операций чтения (все GET-запросы).
    · Гибкая фильтрация данных по операциям и группам хостов для снижения объёма передаваемой информации.
    · Модульная архитектура, позволяющая легко добавлять новые проверки без изменения ядра.

    Место в экосистеме мониторинга:
    S выступает в роли агрегатора и кэширующего прокси между системами мониторинга (например, Grafana через Infinity datasource) и целевыми сервисами. Он берёт на себя периодический сбор данных, снижая нагрузку на сеть и проверяемые системы, а также обеспечивает единый формат ответов для различных источников.

2. Ключевые принципы работы

    · Модульность. Каждый модуль – независимый компонент, реализующий конкретную проверку. Модули загружаются динамически из папки modules/ при старте сервера. Они не зависят друг от друга и не влияют на ядро.
    · Кэширование. Все результаты проверок хранятся в оперативной памяти в структурированном виде. Фоновая задача обновляет кэш с заданной периодичностью. Также предусмотрен эндпоинт /refresh для принудительного обновления.
    · Разделение операций чтения и обновления. Все GET-запросы (кроме /refresh) являются лёгкими – они только читают кэш и возвращают данные мгновенно (время ответа – миллисекунды). Эндпоинт /refresh (доступен как GET, так и POST) инициирует синхронное выполнение всех модулей и обновление кэша. Это гарантирует предсказуемую скорость ответа для систем мониторинга.
    · Фильтрация по группам. Позволяет запрашивать результаты только для хостов, в имени которых (в первом лейбле FQDN) содержится заданный суффикс или подстрока. Например, запрос /v3/portcheck/PGL вернёт данные только для хостов, содержащих PGL в первом лейбле (регистронезависимо). Это снижает объём передаваемых данных и ускоряет ответ.

3. Логическая модель данных

    Формат ключей в модулях:

    · Общий вид: {префикс_операции}.{хост}.{порт} (если порт применим). Пример: portcheck.ims-g201AQL.22, dns.ims-g201AQL.
    · Для HTTP-модуля, где на одном хосте:порту может быть несколько эндпоинтов, ключ дополняется методом и путём: {prefix}.{first_label}.{port}.{method}.{path_escaped}. Пример: http.jolokia-host.8161.POST._console_jolokia.

    Структура кэша в памяти:
    Кэш представляет собой вложенный словарь, где верхний уровень – операции (модули), второй уровень – хосты, третий (если есть) – порты или детали:

    ```json
    {
      "timestamp": "2026-08-17T12:00:00",
      "portcheck": {
        "ims-g201AQL": {"22": true, "6060": false}
      },
      "http": {
        "jolokia-host": {"8161.POST._console_jolokia": true}
      }
    }
    ```

    Форматы ответов API:

    Эндпоинт Формат Описание
    / Массив { "ключ": значение } Устаревший формат для обратной совместимости
    /v2 Массив { "operation": "...", "host": "...", "value": { ... } } Группировка портов в объект для каждого хоста
    /v3 Массив { "operation": "...", "host": "...", "value": "...", "port": "..." } Каждая пара (хост, порт) – отдельная запись
    /v3/{op} То же, что /v3, но только для указанной операции Фильтрация по операции
    /v3/{op}/{groups} То же, с дополнительной фильтрацией по группам хостов Фильтрация по подстроке в первом лейбле

4. Архитектура системы

    Компоненты:

    1. Ядро S – HTTP-сервер на базе Python, отвечающий за приём запросов, управление кэшем, загрузку модулей, фоновую задачу и многопоточную обработку.
    2. Модули – отдельные Python-файлы, каждый содержит функцию run(config) -> dict, выполняющую проверку и возвращающую словарь с результатами.
    3. Кэш – глобальный словарь в памяти, защищённый блокировкой RLock, обеспечивающий быстрый и безопасный доступ.
    4. Фоновая задача – поток, периодически запускающий обновление кэша (выполнение всех модулей) с заданным интервалом (refresh_interval).
    5. Многопоточный HTTP-сервер – на базе socketserver.ThreadingMixIn с ограничением числа одновременных запросов (max_workers).

    Взаимодействие компонентов:

    · При старте S загружает модули из папки modules/, считывает их конфиги и сохраняет в глобальную структуру.
    · Запускается фоновый поток, который сразу выполняет первое обновление кэша, затем повторяет его с интервалом refresh_interval.
    · HTTP-запросы обрабатываются параллельно (до max_workers одновременно). Все GET-запросы читают кэш (блокировка на чтение), а /refresh выполняет модули синхронно и обновляет кэш (блокировка на запись).
    · Модули выполняются с таймаутом (module_timeout), чтобы избежать зависаний.

5. Сценарии использования

    · Мониторинг доступности сервисов: проверка TCP-портов (SSH, HTTP, базы данных), DNS-разрешений, HTTP-статусов (с проверкой содержимого) на множестве хостов.
    · Интеграция с Grafana через Infinity datasource: быстрые GET-запросы к /v3/{op}/{groups} для отображения статусов в панелях. Настройка автоматического обновления через фоновое кэширование.
    · Принудительное обновление данных: использование эндпоинта /refresh по расписанию (например, через cron) или вручную для синхронизации кэша.
    · Тестирование и отладка: использование модуля dummy для генерации тестовых данных или модуля gettime для получения временных меток.

6. Ограничения и допущения

    · Размер кэша не ограничен явно – хранится в оперативной памяти; для больших инфраструктур рекомендуется мониторинг использования памяти.
    · Максимальное число групп в одном запросе – 10 суффиксов (для защиты от перегрузки).
    · Таймаут модулей: каждый модуль должен завершиться за module_timeout (по умолчанию 30 сек). Превышение приводит к игнорированию результатов и логированию ошибки.
    · Однопоточное выполнение модулей внутри ядра: каждый модуль вызывается последовательно, но автор модуля может использовать внутреннюю многопоточность.
    · Зависимость от сети и сторонних систем: модули могут зависеть от доступности проверяемых хостов и сервисов, что может влиять на время обновления кэша.
    · Регистр групп при фильтрации не учитывается (все строки приводятся к верхнему регистру).

    ---

7. Безопасность и производительность

    · CORS – включены заголовки Access-Control-Allow-Origin: *, что позволяет использовать API из браузерных приложений и Grafana.
    · Ограничение числа одновременных запросов – параметр server.max_workers (по умолчанию 20) предотвращает перегрузку сервера.
    · Таймауты на выполнение модулей и фоновых задач защищают систему от зависаний.
    · Многопоточность обеспечивает параллельную обработку запросов, но ограничена семафором для контроля нагрузки.
    · Учётные данные (пароли) хранятся в отдельном файле с правами 600, используются через ссылки auth_ref, маскируются в логах.

    ---

8. Заключение

    Сервер S представляет собой гибкое, производительное и масштабируемое решение для агрегации данных мониторинга. Его архитектура, основанная на модульности и кэшировании, позволяет легко адаптироваться к изменениям инфраструктуры и минимизировать нагрузку на системы. Рекомендуется к использованию в средах с большим количеством хостов и высокими требованиями к скорости отклика.

    Дорожная карта развития:

    · Добавление аутентификации (API-ключи) для защиты эндпоинтов.
    · Возможность хранения кэша во внешнем хранилище (Redis) для масштабирования.
    · Расширение форматов фильтрации (регулярные выражения, исключения).
    · Добавление метрик Prometheus для мониторинга состояния самого S.

2. Руководство администратора

1. Введение

    Руководство предназначено для администраторов, устанавливающих, настраивающих и обслуживающих сервер S. Оно содержит инструкции по развёртыванию, конфигурированию, запуску, мониторингу и устранению типовых проблем.

    Требования к окружению:

    Функциональные особенности:

    · Все GET-запросы читают кэш и возвращают данные мгновенно.
    · Фоновое обновление кэша выполняется с заданным интервалом.
    · Эндпоинт /refresh позволяет принудительно обновить кэш.

2. Установка

    Получение дистрибутива:
    Скопируйте файлы сервера на целевую машину:

    · server.py – основной скрипт.
    · config.yaml – конфигурационный файл.
    · Папка modules/ с модулями и их конфигами.
    · (Опционально) файл секретов secrets.yaml (разместить в защищённом месте).

    Установка зависимостей:

    ```bash

    ```

    Создание структуры каталогов (рекомендуемая):

    ```bash
    mkdir -p /opt/s/modules
    mkdir -p /opt/s/logs
    # Разместите server.py и config.yaml в /opt/s
    ```

3. Конфигурация

    Файл config.yaml содержит все настройки сервера. Пример с пояснениями:

    ```yaml
    host: "0.0.0.0"                 # IP-адрес для прослушивания
    port: 8080                      # Порт
    modules_dir: "./modules"        # Путь к папке с модулями

    server:
      max_workers: 20               # Максимальное число одновременно обрабатываемых запросов

    cache:
      refresh_interval: 60          # Интервал обновления кэша в секундах

    module_timeout: 30              # Максимальное время выполнения одного модуля (сек.)

    logging:
      level: INFO                   # Уровень логирования: DEBUG, INFO, WARNING, ERROR, CRITICAL
      format: "%(asctime)s - %(name)s - %(levelname)s - %(message)s"
      datefmt: "%Y-%m-%d %H:%M:%S"
      file: "logs/server.log"       # Путь к файлу лога (если не указан, вывод в консоль)
      max_bytes: 10485760           # Размер файла до ротации (10 МБ)
      backup_count: 5               # Количество сохраняемых архивов
      module_levels:                # Переопределение уровня для отдельных модулей
        dns: DEBUG
    ```

    Параметры можно изменять в любое время, но для применения изменений требуется перезапуск сервера.

4. Управление модулями

    · Добавление модуля: поместите файл модуля (имя_модуля.py) и его конфиг (имя_модуля.yaml) в папку modules/. При перезапуске сервера модуль будет автоматически загружен.
    · Удаление модуля: удалите соответствующие файлы. Сервер не требует перезагрузки, но изменения вступят в силу только после перезапуска.
    · Проверка загрузки: при старте в логах отображается список загруженных модулей с их версиями и путями к конфигам.

    Особенности модуля http_check:

    · Для работы с авторизацией создайте отдельный файл секретов (например, /etc/s/secrets.yaml) с правами 600.
    · В конфиге модуля http_check.yaml укажите путь к этому файлу через параметр secrets_file.
    · В списке endpoints используйте auth_ref для ссылки на секрет.

5. Запуск и остановка сервера

    Ручной запуск:

    ```bash
    cd /opt/s
    python3 server.py
    ```

    Запуск через systemd (рекомендуется):
    Создайте файл /etc/systemd/system/s-server.service:

    ```ini
    [Unit]
    Description=S Server
    After=network.target

    [Service]
    Type=simple
    User=your_user
    WorkingDirectory=/opt/s
    ExecStart=/usr/bin/python3 /opt/s/server.py
    Restart=always
    RestartSec=10

    [Install]
    WantedBy=multi-user.target
    ```

    Затем выполните:

    ```bash
    sudo systemctl daemon-reload
    sudo systemctl enable s-server
    sudo systemctl start s-server
    ```

    Остановка: нажмите Ctrl+C при ручном запуске или выполните sudo systemctl stop s-server.

6. Логирование

    Логи пишутся в файл, указанный в logging.file, или в консоль. Автоматическая ротация происходит при достижении max_bytes; старые файлы архивируются (server.log.1, server.log.2, …).

    Ключевые сообщения и их значение:

    · Logging configured – логирование настроено.
    · Loaded module: xxx (version x.x.x) – модуль успешно загружен.
    · Cache updated successfully at ... – кэш обновлён.
    · Module execution timed out after 30s – модуль превысил таймаут.
    · Cache update timed out in background worker – фоновое обновление не уложилось в таймаут.
    · Key '...' already exists, overwriting – конфликт ключей между модулями.

    Уровни логирования:

    · DEBUG – детали выполнения модулей, полезна при отладке.
    · INFO – обычные события (запросы, обновления кэша).
    · WARNING – нештатные, но не критичные ситуации.
    · ERROR – сбои модулей, таймауты, сетевые ошибки.

7. Тестирование работоспособности

    Базовые проверки с использованием curl:

    · Проверка здоровья (любой эндпоинт):
      ```bash
      curl -s http://localhost:8080/ | jq
      ```
      Ожидаемый ответ: JSON-массив (может быть пустым, если кэш ещё не заполнен).
    · Получение данных в формате /v3 для операции portcheck:
      ```bash
      curl -s http://localhost:8080/v3/portcheck | jq
      ```
    · Фильтрация по группам (например, PGL):
      ```bash
      curl -s http://localhost:8080/v3/portcheck/PGL | jq
      ```
    · Принудительное обновление кэша:
      ```bash
      curl -X POST http://localhost:8080/refresh
      ```
      Ответ: {"status":"ok","timestamp":"2026-08-17T12:00:00"}
    · Проверка HTTP-модуля:
      ```bash
      curl -s http://localhost:8080/v3/http | jq
      ```

8. Мониторинг и обслуживание

    · Актуальность кэша: проверяйте время последнего обновления в логах или используйте модуль gettime, который возвращает completion_time в ответах.
    · Очистка кэша: перезапуск сервера или вызов /refresh для перезаписи.
    · Дисковое пространство: следите за размером лог-файлов; автоматическая ротация настроена.
    · Мониторинг процессов: используйте systemd или внешний мониторинг для контроля состояния сервера.

9. Устранение неполадок

    Проблема Возможное решение
    Модуль не загружается Проверьте наличие файла .py, функции run, синтаксис Python. Смотрите логи ошибок загрузки.
    Ответ – пустой массив Кэш пуст – выполните /refresh вручную или дождитесь фонового обновления. Проверьте, что модули возвращают данные.
    Таймауты или медленные ответы Увеличьте module_timeout или refresh_interval. Проверьте сетевую доступность целевых хостов.
    Сервер не стартует Проверьте синтаксис config.yaml, доступность порта, права на каталог логов.
    Ошибка SyntaxError: invalid syntax Используйте Python 3.6 или новее. Обновите Python или установите из PPA.
    Предупреждения SSL Они подавлены в модуле http_check, но если появляются, добавьте urllib3.disable_warnings() в модуль.

10. Приложение: Полный пример config.yaml

    ```yaml
    host: "0.0.0.0"
    port: 8080
    modules_dir: "./modules"
    server:
      max_workers: 20
    cache:
      refresh_interval: 60
    module_timeout: 30
    logging:
      level: INFO
      file: "logs/server.log"
      format: "%(asctime)s - %(name)s - %(levelname)s - %(message)s"
      datefmt: "%Y-%m-%d %H:%M:%S"
      max_bytes: 10485760
      backup_count: 5
      module_levels: {}
    ```

3. Руководство программиста

1. Введение

    Руководство предназначено для разработчиков, создающих новые модули для сервера S, а также для тех, кто хочет понять внутреннее устройство системы или модифицировать её.

    S – это модульный HTTP-сервер с кэшированием. Ядро обеспечивает загрузку модулей, управление кэшем, многопоточную обработку запросов и фоновое обновление. Модули – это независимые компоненты, каждый из которых реализует функцию run(config) -> dict, возвращающую результаты проверок.

    ---

2. Логическая модель и архитектура

    Поток данных:

    · GET-запрос → обработчик → чтение глобального кэша (CACHE) → формирование ответа → отправка.
    · /refresh → синхронный вызов update_cache() → выполнение всех модулей → запись в CACHE → ответ.

    Глобальные структуры:

    · MODULES – словарь, где ключ – имя модуля (нормализованное, без подчёркиваний), значение – словарь с полями run (функция), config (конфиг модуля), version, config_path.
    · CACHE – словарь, структурированный как {operation: {host: value_or_dict}}, защищённый блокировкой CACHE_LOCK (RLock).
    · CACHE_TIMESTAMP – строка ISO с временем последнего обновления.

    Блокировки: CACHE_LOCK используется при чтении (копирование кэша) и записи (обновление). Для чтения достаточно блокировки на время копирования.

    ---

3. Интерфейс модуля

    Каждый модуль должен предоставлять функцию:

    ```python
    def run(config: dict) -> dict:
        ...
    ```

    · config – словарь, загруженный из файла конфигурации модуля (YAML или JSON).
    · Возвращаемое значение – словарь, где ключи – строки, значения – любые JSON-сериализуемые (bool, int, float, str, dict, list).

    Правила формирования ключей:
    Для совместимости с фильтрацией по группам и форматами ответов рекомендуется использовать префикс операции и имя хоста (и порт, если применимо):

    · {префикс}.{хост} – для операций без порта.
    · {префикс}.{хост}.{порт} – для операций с портами.
    · Для модуля http_check с несколькими эндпоинтами на одном хосте:порту ключ дополняется методом и путём: {prefix}.{first_label}.{port}.{method}.{path_escaped}.

    Примеры:

    · Модуль DNS: {"dns.ims-g201AQL": True, "dns.ims-g202KFL": False}
    · Модуль portcheck: {"portcheck.ims-g201AQL.22": True, "portcheck.ims-g201AQL.6060": False}
    · Модуль http: {"http.jolokia-host.8161.POST._console_jolokia": True}

    Префикс должен быть уникальным среди модулей.

    ---

4. Конфигурация модуля

    Файл конфигурации должен иметь то же имя, что и модуль, с расширением .yaml (или .json). Например, для portcheck.py – portcheck.yaml.

    Рекомендуется включать параметры:

    · prefix – строковый префикс для ключей.
    · hosts или endpoints – список целевых объектов (хосты, порты, пути).
    · Специфичные для модуля параметры (таймауты, пути, и т.д.).

    Пример http_check.yaml:

    ```yaml
    prefix: "http"
    secrets_file: "/etc/s/secrets.yaml"
    max_workers: 20
    log_level: "summary"
    defaults:
      timeout: 3
      method: "GET"
      expected_status: 200
      ssl: auto
      check_content: null
      headers: {}
    endpoints:
      - host: "jolokia-host.example.com"
        port: 8161
        path: "/console/jolokia"
        method: "POST"
        ssl: true
        auth_ref: "jolokia_creds"
        headers:
          Origin: "https://jolokia-host.example.com:8161"
        body: '{"type":"read","mbean":"java.lang:type=Memory"}'
    ```

    ---

5. Версионирование

    Каждый модуль должен содержать глобальную переменную VERSION (строку). Она отображается в логах при загрузке.

    Рекомендуется использовать семантическое версионирование (MAJOR.MINOR.PATCH):

    · MAJOR – несовместимые изменения (например, изменение формата возвращаемых данных).
    · MINOR – добавление новой функциональности без нарушения совместимости.
    · PATCH – исправления ошибок.

    ---

6. Разработка нового модуля: пошаговая инструкция

    1. Создайте файл в папке modules/, например, my_check.py.
    2. Реализуйте функцию run(config).
    3. Добавьте переменную VERSION.
    4. Организуйте логирование с использованием logger = logging.getLogger(__name__).
    5. Создайте конфиг my_check.yaml в той же папке.
    6. Протестируйте модуль изолированно (вызовите run с тестовым конфигом).
    7. Запустите сервер и проверьте, что модуль загружается и его данные появляются в ответах.
    8. Используйте таймауты и обработку исключений для сетевых операций.

Шаблон модуля:

```python
import logging

VERSION = "1.0.0"
logger = logging.getLogger(__name__)

def run(config: dict) -> dict:
    logger.info("Module started")
    # Ваша логика
    result = {}
    # ... заполнение result
    logger.info("Module finished, returning %d keys", len(result))
    return result
```

7. Расширенные возможности

· Параллелизм внутри модуля. Для ускорения проверок используйте concurrent.futures.ThreadPoolExecutor (как в модуле portcheck или http_check). Это безопасно, т.к. модули выполняются в отдельных потоках ядра.
· Таймауты. Устанавливайте собственные таймауты на сетевые операции (например, параметр timeout в socket.create_connection или requests), чтобы не полагаться только на общий module_timeout.
· Логирование. Используйте разные уровни (debug, info, warning, error) для отладки и мониторинга.
· Секреты. Для хранения учётных данных предусмотрите механизм, аналогичный http_check: отдельный файл с правами 600 и ссылки через auth_ref. В модуле вы можете использовать функцию load_secrets для чтения секретов.

---

8. Тестирование и отладка модуля

· Локальный запуск: импортируйте модуль и вызовите run с тестовым конфигом в отдельном скрипте.
· Включение DEBUG логов: установите в config.yaml для вашего модуля уровень DEBUG, чтобы видеть все сообщения.
· Проверка совместимости: убедитесь, что возвращаемые ключи соответствуют ожидаемым форматам для /v2 и /v3 (особенно для портов).

10. Приложение: Примеры модулей

Пример модуля dummy.py:

```python
import logging
VERSION = "1.0.0"
logger = logging.getLogger(__name__)

def run(config):
    count = config.get('count', 5)
    prefix = config.get('prefix', 'dummy')
    result = {}
    for i in range(1, count+1):
        result[f"{prefix}.{i}"] = f"dummy_{i}"
    return result
```

Пример модуля gettime.py:

```python
from datetime import datetime
VERSION = "1.0.0"

def run(config):
    key = config.get('key_name', 'completion_time')
    fmt = config.get('time_format', '%Y-%m-%dT%H:%M:%S')
    return {key: datetime.now().strftime(fmt)}
```

· Формирует ключи с методом и путём.
· Имеет три уровня логирования (full, summary, errors).
